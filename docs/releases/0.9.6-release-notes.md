# AssegaiPHP Core 0.9.6

Released: 2026-08-24

`0.9.6` fixes route resolution for controller-bearing modules that are imported by more than one parent module.

Shared modules can now serve routes through every parent path and host scope. This supports applications that compose multiple surfaces—such as an API and control plane—from one Assegai application without duplicating feature modules or controllers.

## Highlights

### Correct routes for modules with multiple parents

Previously, controller discovery stored one resolved route context per module and controller class. It also marked a module as globally visited after its first traversal. Although the module graph correctly recorded every parent, the routing graph kept only the first parent mount. Requests through later parents therefore returned `404`, and reversing import order merely changed which route worked.

Core now records each distinct module mount as a route context. A shared controller can be reached through every path contributed by its parents:

```text
ApplicationModule
├── ApiModule ──────────┐
│   /api                ├── SharedFeatureModule → /shared
└── ControlPlaneModule ─┘
    /control
```

The shared feature routes are available at both `/api/shared` and `/control/shared`. Parent import order no longer determines which mount survives.

Host constraints are part of the same route context. If the parents mount a shared module under different host scopes, each host receives the correct route without leaking access to unmatched hosts.

### Graph-safe resolution without duplicate application state

Route contexts are metadata only. A module imported by multiple parents does not acquire duplicate provider ownership, controller definitions, or application state.

Core deduplicates identical diamond mounts while preserving mounts whose path or host constraints differ. Module graph analysis is iterative and identifies strongly connected components before expanding routes. Cyclic imports remain bounded, but valid finite routes through different cycle entry points are retained.

At request time, the router visits each applicable module mount once and continues to prune branches by path and host. The selected mount is associated with the activated controller instance through a weak reference, keeping interleaved or long-lived request handling isolated without retaining completed controllers in memory.

### Consistent middleware and OpenAPI behavior

Controller-bound middleware now expands across every resolved mount of a shared controller. Rebuilding the module graph invalidates the middleware route cache, preventing route metadata from one application graph from leaking into another graph in the same process.

Generated OpenAPI documents also include every distinct mounted path. Operations receive unique identifiers when the same handler is available at multiple paths. When multiple host-scoped parents mount the same handler at an identical path, their server alternatives are merged into one operation rather than one host silently overwriting another.

## Upgrade Notes

No application changes are required.

Applications that previously duplicated a controller-bearing module to work around the second-parent `404` can remove that duplication and import the same module from each intended parent.

The existing compatibility accessors that return one canonical controller path continue to do so. Routing, middleware, and OpenAPI generation use the complete route-context graph internally.

## Validation

This release adds regression coverage for:

- shared controller routes mounted through two parent paths
- parent import-order independence
- inherited host scopes and rejection of unmatched hosts
- identical diamond-mount deduplication
- shared modules participating in cyclic import graphs
- isolation between interleaved activated controller instances
- controller-bound middleware across every mount
- OpenAPI paths, operation identifiers, and merged host servers

The Core unit suite passes with 206 tests and 698 assertions. PHPStan level 8 reports no errors.
