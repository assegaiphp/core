# AssegaiPHP Core 0.10.0

AssegaiPHP 0.10.0 delivers configurable authentication failure handling and a complete exception-filter lifecycle.

Browser controllers can now translate a guard's `UnauthorizedException` into a login redirect without changing guard semantics or adding an auth interceptor. API controllers retain the normal `401 Unauthorized` response when the redirect filter is not applied.

## Highlights

### Complete exception-filter lifecycle

- global, controller, and handler filters are registered reliably
- filter class names resolve through dependency injection
- configured filter instances remain supported
- precedence is handler, controller, then global
- the first matching filter handles the exception terminally
- Core emits one response for a handled exception
- filters run before the request session closes

`UseFilters` accepts multiple definitions, and global filters can be registered with `AppInterface::useGlobalFilters()`.

### Configurable browser-login redirects

`LoginRedirectFilter` is built in but opt-in. Applications apply it only to browser routes that should redirect.

The filter supports:

- an application-supplied login URL
- redirect statuses `301`, `302`, `303`, `307`, and `308`
- safe intended-target retention for `GET` and `HEAD`
- a configurable dot-delimited session key
- additional excluded paths
- automatic exclusion of the login path to prevent loops
- `Cache-Control: no-store` on redirect and excluded-path responses

Cross-origin, scheme-relative, malformed, and unsafe targets are not stored. Applications can pass a configured filter instance or replace the built-in filter with a bespoke `ExceptionFilterInterface` implementation.

### Dedicated authentication configuration

Core now composes `config/auth.php` into the application configuration cascade:

1. `config/default.php`
2. `config/auth.php`
3. production and local overrides when present
4. `config/secure.php`

When `LoginRedirectFilter` is registered by class name, it reads `authentication.loginRedirect` from the active application's configuration through DI. Framework-owned session cookie settings can live alongside that policy in `config/auth.php`. Sensitive values remain in `config/secure.php`.

### Session behavior needed by login flows

Nested session reads now honor their supplied default. Nested values can be removed and retrieved once with `Session::remove()` and `Session::pull()`. This supports intended-target restoration without leaving stale redirects in the session.

## What is not included

- no auth interceptor is required or introduced
- redirect behavior is not enabled globally by default
- `OnException` metadata in `assegaiphp/attributes` is unchanged
- entity-driven database sync is not part of 0.10.0; it remains a likely post-1.0 roadmap candidate

## Validation

The release regression lane covers DI resolution, handler/controller/global precedence, terminal handling, configured redirects, loop prevention, safe and unsafe intended targets, session persistence, API 401 behavior, and single response emission. The complete Core test suite and PHPStan level 8 are release gates.
