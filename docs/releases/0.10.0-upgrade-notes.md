# Upgrade to AssegaiPHP Core 0.10.0

## Path

- From: `0.9.x`
- To: `0.10.0`

## Automatic package alignment

Assegai Console 0.10 updates installed 0.9-line Core, ORM, Auth, Collections, Common, Forms, Util, and Validation constraints to `^0.10.0`. New projects also select Core `^0.10.0` and include `config/auth.php`.

Review and commit the resulting `composer.json` changes according to your application's dependency policy. Existing lock files should be updated by the application through its normal Composer workflow; the framework release-preparation commits do not rewrite them.

## Existing session configuration

Existing `session` settings in `config/default.php` remain supported. Core loads that file before `config/auth.php`, so applications can move the block when they are ready.

For the new dedicated layout, add `config/auth.php`:

```php
<?php

return [
  'authentication' => [
    'loginRedirect' => [
      'url' => '/auth/login',
      'statusCode' => 302,
      'preserveTarget' => true,
      'targetSessionKey' => 'auth.intended_url',
      'excludedPaths' => [],
    ],
  ],
  'session' => [
    'name' => 'assegai_session',
    'cookieLifetime' => 0,
    'cookiePath' => '/',
    'cookieDomain' => '',
    'cookieSecure' => null,
    'cookieHttpOnly' => true,
    'cookieSameSite' => 'Lax',
  ],
];
```

Set `authentication.loginRedirect.url` to the public login route owned by your application. Do not leave the scaffold value unchanged unless that route actually exists.

## Opt in browser controllers

Apply the filter only where an unauthenticated browser should be redirected:

```php
#[UseGuards(SessionAuthGuard::class, UnauthorizedException::class)]
#[UseFilters(LoginRedirectFilter::class)]
final class DashboardController
{
}
```

Do not apply it to API-only controllers. With only the guard in place, `UnauthorizedException` follows Core's normal 401 response path.

Applications that need a controller-specific redirect policy can pass a configured `LoginRedirectFilter` instance. Applications with behavior outside the built-in option surface can supply their own exception filter.

## Review custom exception filters

Custom filters must implement `ExceptionFilterInterface::catch(Throwable $throwable, ArgumentsHost $host): void`.

If the same exception has filters at several scopes, verify that the intended order is:

1. handler
2. controller
3. global

The first matching filter is terminal. It owns the response, and Core will not run lower-precedence filters or emit a second exception response.

## Session login flow

Use `SessionAuthStrategy` after your application loads the user. A successful login verifies the password, rotates the session identifier, and stores a sanitized user. Restore the safe target once with `Session::pull('auth.intended_url', $fallback)` and redirect with 303 after a form POST.

See [Session Authentication End to End](../session-authentication.md) for the complete user lookup, service, guard, controller, login, and logout example.

## Database sync roadmap reconciliation

The former 0.10 database-sync upgrade draft was stale and has been removed. The underlying design remains in the ORM's `docs/entity-driven-database-sync-plan.md`; the roadmap currently treats that work as a likely post-1.0 candidate. This release does not assign it to 0.11.0.

## Verification

- visit a protected browser URL and confirm it redirects to the configured login route
- confirm the safe original URL is restored after successful login
- confirm the login route itself cannot enter a redirect loop
- request a protected API route without the redirect filter and confirm it returns 401 with no `Location` header
- submit an unsafe or cross-origin intended target and confirm it is not persisted
- confirm login and logout rotate or destroy the session as expected
- run the application's complete test and static-analysis lanes
