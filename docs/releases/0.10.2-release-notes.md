# AssegaiPHP Core 0.10.2

Core 0.10.2 separates application Web Component runtime policy from tracked workspace build defaults. Applications can serve integrity-pinned scripts without rewriting `assegai.json` or losing development hot reload.

## What changed

- adds validated application `webComponents` overrides with independent controls for automatic bundle emission and hot-reload polling
- shares one lazy, project-bound rendering snapshot across both engines and the public Web Component helpers, cleared at request completion and after failures
- adds `AppConfig::current()` for reading the active application's configuration without loading fragments again, plus `WebComponentSupport::getConfiguration()` for inspecting effective runtime policy
- uses the same application snapshot for document script definitions and automatic runtime policy, retaining the existing SRI attribute renderer
- removes ambient legacy configuration precedence for document defaults inside App requests; standalone rendering keeps the legacy lookup
- makes direct `new View(...)` calls with omitted properties use configured document defaults, matching the `view(...)` helper
- escapes watcher URLs safely inside inline polling scripts

## Compatibility

PHP 8.4 or newer remains required. No dependency versions change. Workspace build configuration and development watcher behavior remain available when no application override is supplied.

Application overrides accept `enabled`, `bundleUrl`, and `hotReload.enabled`, `hotReload.path`, and `hotReload.pollInterval`. Invalid types or unknown fields fail explicitly. Build-only fields stay in `assegai.json`.

## Upgrade notes

For an application that owns verified production scripts, set both `webComponents.enabled` and `webComponents.hotReload.enabled` to `false` in application configuration. Disabling automatic bundle emission alone does not disable polling or manually configured scripts.

Derive verified script definitions and runtime policy from one application-owned selection value. Read it through `AppConfig::current()` after factory creation and in request services, not through a separate legacy configuration load. Missing or corrupt selection must not restore unsigned automatic execution. Restart long-lived workers after deployment configuration changes.

Code that changed document defaults through `Config::set('app', ...)` or `$_ENV['app']` during an App request must use application configuration or explicit render properties instead. Explicit `ViewProperties` are still honored.

See [Frontend with Web Components](../frontend-with-web-components.md#application-runtime-overrides) for configuration and lifecycle details.
