# AssegaiPHP Core 0.9.5

Released: 2026-08-19

`0.9.5` adds application-level Cross-Origin Resource Sharing (CORS) support to Core.

Applications can now configure one CORS policy at the Assegai application boundary, including credentialed origin allowlists, preflight caching, custom headers, and dynamic per-request policies. The same policy is applied to preflight and actual responses across the PHP and OpenSwoole runtimes.

## Highlights

### NestJS-style `enableCors()` configuration

Call `enableCors()` before `run()` to opt into the default policy:

```php
$app = AssegaiFactory::createFromProject(AppModule::class, __DIR__);
$app->enableCors();
$app->run();
```

The default policy allows any origin without credentials and advertises `GET`, `HEAD`, `PUT`, `PATCH`, `POST`, and `DELETE` for preflight requests.

Applications that use cookies, HTTP authentication, or another credentialed browser flow can configure an explicit origin allowlist:

```php
$app->enableCors([
  'origin' => [
    'http://localhost:5173',
    'https://console.example.com',
  ],
  'credentials' => true,
  'methods' => ['GET', 'HEAD', 'POST', 'PUT', 'PATCH', 'DELETE'],
  'allowedHeaders' => [
    'Content-Type',
    'Authorization',
    'X-CSRF-Token',
  ],
  'exposedHeaders' => ['Location'],
  'maxAge' => 600,
]);
```

The configuration surface supports:

- string, list, boolean, and callback-based origin policies
- string or list-based method configuration
- configured or safely reflected request headers
- exposed response headers
- credentialed requests with explicit origins
- browser preflight caching through `Access-Control-Max-Age`
- configurable successful preflight status codes
- optional continuation of preflight requests through normal routing
- request-level policy callbacks for path-, tenant-, or environment-specific behavior

Configuration is available as an options array or a typed `CorsOptions` object. Unsafe combinations such as `credentials: true` with a wildcard origin are rejected during application bootstrap.

### Correct preflight handling

Core recognizes a CORS preflight only when an `OPTIONS` request includes both `Origin` and `Access-Control-Request-Method`. Ordinary application `OPTIONS` routes continue through normal routing.

By default, a valid preflight is completed before sessions, module graph preparation, routing, middleware, and controller execution. Applications that deliberately own preflight routing can set `preflightContinue` to `true`.

Preflight responses now include the configured methods, headers, credentials, cache duration, and appropriate `Vary` values. When `allowedHeaders` is omitted, Core reflects the requested header names and varies the response by `Access-Control-Request-Headers`.

### Consistent CORS headers on real responses

CORS is no longer limited to a front-controller header shim. Core decorates the final framework response, including static resources and error responses, immediately before it is emitted.

This means a successful preflight does not imply that a route exists, but the subsequent `404`, `405`, or `500` response carries the same applicable CORS policy. Browser clients can therefore observe the real HTTP result instead of receiving a generic CORS failure caused by missing headers on the actual response.

Origin allowlists and callbacks emit `Vary: Origin`, preserving existing `Vary` values. Requests from disallowed origins fail closed and receive no `Access-Control-Allow-Origin` header.

### PHP 8.5-compatible test tooling

The development test baseline now requires Codeception `^5.3.5`, which contains the PHP 8.5 compatibility fixes needed by the suite.

`composer test` explicitly enables `register_argc_argv`, reports all PHP errors, and configures Codeception to convert deprecations into test failures. This keeps current deprecations visible and prevents compatibility regressions from being hidden ahead of future PHP releases.

## Upgrade Notes

CORS remains disabled until an application calls `enableCors()`, so existing applications do not acquire a new cross-origin policy automatically.

Applications migrating from the scaffold CORS shim should:

1. Remove unconditional `Access-Control-Allow-*` headers from the project-root `index.php`.
2. Remove the top-level `OPTIONS` short-circuit from `index.php`.
3. Remove Apache or reverse-proxy CORS directives that would overwrite framework headers.
4. Add one authoritative `$app->enableCors(...)` policy in `bootstrap.php` before `$app->run()`.

Do not combine `Access-Control-Allow-Origin: *` with `Access-Control-Allow-Credentials: true`. Use an explicit origin allowlist or callback whenever credentials are enabled.

Because `enableCors()` is now part of `AppInterface`, custom implementations and test doubles that implement this interface must add the new method:

```php
use Assegai\Core\Http\Cors\CorsOptions;

public function enableCors(CorsOptions|array|callable|null $options = null): static;
```

Applications using cross-site cookies must still configure appropriate `SameSite` and `Secure` cookie attributes and protect state-changing routes against CSRF. CORS controls browser access to responses; it is not a replacement for authentication or CSRF protection.

## Validation

This release adds or updates regression coverage for:

- default and credentialed CORS policies
- wildcard and credential validation
- static and callback-based origin resolution
- allowed and disallowed origins
- ordinary `OPTIONS` requests versus CORS preflights
- configured and reflected request headers
- exposed headers and preflight cache duration
- preservation and composition of `Vary` headers
- preflight short-circuiting and `preflightContinue`
- PHP and OpenSwoole response emission
- CORS headers on successful, static, and error responses
- PHP 8.5 deprecation handling in the test runner

For full configuration details and migration examples, see the [CORS guide](../cors.md).
